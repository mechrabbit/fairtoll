# Spike: per-request prices with the official x402 packages

This spike answers issue #3. The question from the README is whether `@x402/core` handles a different price on each request cleanly. It does. One constraint comes with that answer. The price for a request must be the same when the server sends the 402 and when the agent retries with payment. If the price changes in between, the paid retry is rejected.

Everything below was checked against `@x402/*` 2.28.0, the version on npm on 2026-10-21. Source citations point at the published `dist/esm` bundles, with the original source file named from the bundle's `// src/...` banner. The runnable snippets live in `spikes/x402/`. Run `npm install` there, then the scripts listed in [Run the snippets](#run-the-snippets).

## Packages a charging server uses

| Package | Role in Fairtoll |
| --- | --- |
| `@x402/core` | Transport-agnostic server. `x402ResourceServer` talks to the facilitator. `x402HTTPResourceServer` turns an HTTP request into a 402, a verified payment, or a pass-through. `HTTPFacilitatorClient` calls a remote facilitator over `fetch`. Its only runtime dependency is `zod`. |
| `@x402/evm` | The `exact` scheme for EVM chains. Fairtoll registers `ExactEvmScheme` from `@x402/evm/exact/server`. That class turns a price into an atomic USDC amount and asset address, and it holds no signer. |
| `@x402/express`, `@x402/hono`, `@x402/next` | Framework middleware over `@x402/core`. Fairtoll does not need them. See [Build the adapters on `@x402/core`](#build-the-adapters-on-x402core). |
| `@x402/svm`, `@x402/avm` | Solana and Algorand schemes. Out of scope for v1, but they register the same way. |

The client side, used only by the spike scripts and by the setup CLI's testnet check, is `@x402/core/client`, `x402HTTPClient` from `@x402/core/http`, and `ExactEvmScheme` from `@x402/evm`.

## Can the price differ per request

Yes. `PaymentOption.price` has type `Price | DynamicPrice`, and `DynamicPrice` is `(context: HTTPRequestContext) => Price | Promise<Price>` (`@x402/core` `dist/esm/x402Client-C7_OogbK.d.mts:820,851`). `payTo` has the same dynamic form.

`x402ResourceServer.buildPaymentRequirementsFromOptions` calls the function on every request, before it builds the requirements (`src/server/x402ResourceServer.ts`, `chunk-FV2JN4FK.mjs:1106-1124`). `x402HTTPResourceServer.processHTTPRequest` calls that builder on the unpaid request and again on the paid retry (`src/http/x402HTTPResourceServer.ts`, `chunk-FV2JN4FK.mjs:2522`).

On the paid retry, `findMatchingRequirements` compares the payload's `accepted` field to the freshly built requirements. The comparison is `paymentRequirementsMatchAccepted`, which runs `deepEqual` on `scheme`, `network`, `amount`, `asset`, `payTo`, and `maxTimeoutSeconds` (`chunk-FV2JN4FK.mjs:1650` and `2046-2058`). A changed amount fails that check, and the server answers 402 with `error: "No matching payment requirements"`.

The `/drifting/` path in `spikes/x402/prices.mjs` returns a higher price on each call. `run-node.mjs` and `run-worker.mjs` both show the result:

```
ok  /drifting/x quoted 1000 then rejected with: No matching payment requirements
```

What this means for the pricing hook:

- The hook is a pure function of the request and the config. A static config price meets that rule.
- The hosted service's hook must return the same quote for a given request for at least `maxTimeoutSeconds`, which defaults to 300. A hook that reprices live will reject paying agents in the gap between the 402 and the retry.
- The hook runs twice for each paid request, once for the 402 and once for the retry. It must be cheap, or the hosted hook must cache its quote.

### How Fairtoll passes its price in

`x402HTTPResourceServer` matches routes from its own route table. Fairtoll already decides the path policy, so the spike gives x402 a single catch-all route `"*"`. That pattern compiles to `^.*?$` for every method (`parseRoutePattern`, `chunk-FV2JN4FK.mjs:3165`). The price function reads the price that Fairtoll's pricing hook already chose, off the adapter Fairtoll built for this request:

```js
const httpServer = new x402HTTPResourceServer(resourceServer, {
  "*": {
    accepts: { scheme: "exact", network, payTo, price: (ctx) => ctx.adapter.price },
    customPaywallHtml: "<!doctype html><p>Payment required</p>",
  },
});
```

The full module is `spikes/x402/charge.mjs`. Fairtoll's policy engine owns "which paths charge", and x402 never sees a second copy of the path rules.

## Does the server code run on Workers and on Node

`@x402/core` and `@x402/evm/exact/server` run on both. The framework middleware has two problems on Workers.

**`@x402/core` needs no Node APIs.** The base64 helpers use `globalThis.btoa` and `atob` when they exist and fall back to `Buffer` only otherwise (`src/utils/index.ts`, `chunk-XW2CWVLZ.mjs:96-115`). `HTTPFacilitatorClient` uses global `fetch`. `run-worker.mjs` bundles `charge.mjs` with esbuild for the browser platform and runs it in workerd through Miniflare 4 with no compatibility flags. All four scenarios pass, the same as on Node 24:

```
== core charger on workerd, no nodejs_compat
ok  /articles/one quoted 2000 and served after settle
ok  /reports/q3 quoted 50000 from an AssetAmount
ok  /drifting/x quoted 1000 then rejected with: No matching payment requirements
ok  /missing/page origin 404 passed through without settlement
```

**`@x402/hono` does not bundle without `nodejs_compat`.** It imports `@x402/extensions`, whose bazaar module imports `domainToASCII` from `"url"` (`@x402/extensions` `dist/esm/chunk-SV2YHMOC.mjs:407`). The middleware also calls `Buffer.from` on the response body (`@x402/hono` `dist/esm/index.mjs`, settlement branch).

**`@x402/hono` fails the first request on Workers even with `nodejs_compat`.** `paymentMiddleware` calls `httpServer.initialize()` when it is constructed. On Workers that means module scope, and workerd rejects the facilitator `fetch` there with "Disallowed operation called within global scope". The middleware drops the failed promise, so the first request returns 500 and the second returns 402:

```
== @x402/hono middleware on workerd, flags=[nodejs_compat]
request 1 status 500 payment-required header: false
request 2 status 402 payment-required header: true
```

`charge.mjs` avoids that failure. It calls `initialize()` inside the first request and clears the cached promise if the call fails.

### Build the adapters on `@x402/core`

Both adapters should call `x402HTTPResourceServer` through one shared charge function and a small `HTTPAdapter` over the Fetch `Request`. The Express adapter converts its request to a `Request`, or implements `HTTPAdapter` over `req` directly. The reasons:

- It runs on Workers without `nodejs_compat` and without the first-request failure.
- Fairtoll keeps control of fail-open. The stock middleware turns facilitator errors into 500 and 502 responses (`@x402/hono` `facilitatorErrorResponse` and `internalErrorResponse`). The README requires the page to serve normally instead.
- One route table, Fairtoll's, decides which paths charge.
- It still builds on the official packages. Fairtoll implements no payment logic, only the adapter interface that `@x402/core` publishes for this purpose.

`HTTPAdapter` needs six methods: `getHeader`, `getMethod`, `getPath`, `getUrl`, `getAcceptHeader`, and `getUserAgent` (`x402Client-C7_OogbK.d.mts:769`). `FetchRequestAdapter` in `charge.mjs` implements them in under 30 lines.

## How verification and settlement work

The flow for the `exact` scheme on EVM, as `charge.mjs` runs it:

1. The unpaid request arrives. `processHTTPRequest` returns `payment-error` with status 402 and a base64 `PAYMENT-REQUIRED` header. The header lists the accepted requirements: scheme, network, atomic `amount`, USDC `asset`, `payTo`, and `maxTimeoutSeconds`.
2. The agent signs an EIP-3009 `transferWithAuthorization` for exactly that amount to `payTo`, and retries with a `PAYMENT-SIGNATURE` header.
3. `processHTTPRequest` rebuilds the requirements, matches them against the payload, and calls the facilitator's `/verify`. The facilitator checks the signature, `authorization.to == payTo`, `authorization.value == amount`, the validity window, the nonce, and the payer's balance. It then simulates the transfer (`@x402/evm` `dist/esm/exact/facilitator/index.mjs:181-222`). A valid payment returns `payment-verified`.
4. Fairtoll serves the origin response. The default `exact` flow is `authorization` (`ExactEvmScheme.paymentFlows`, `@x402/evm` `dist/esm/exact/server/index.mjs`). That flow verifies before the handler and settles after it (`PAYMENT_FLOWS`, `src/server/paymentFlow.ts`, `chunk-FV2JN4FK.mjs:215-220`).
5. If the origin returns 400 or higher, Fairtoll calls `result.cancellationDispatcher.cancel(...)` and returns the origin response. Nothing settles, so the agent pays nothing for a failed page. The `/missing/` scenario shows this.
6. Otherwise Fairtoll calls `processSettlement`. The facilitator submits the transfer on-chain and pays the gas. The server adds the `PAYMENT-RESPONSE` header, which carries the transaction hash, to the response.

`run-node.mjs` records the facilitator calls for the four scenarios. It shows one lazy `/supported` call, a verify for every matched payment, and a settle for only the two served pages:

```
ok  facilitator calls: supported verify settle verify settle verify
```

Three details matter for the charge handler:

- `HTTPFacilitatorClient` defaults to a 90 second timeout (`DEFAULT_TIMEOUT_MS`, `src/http/httpFacilitatorClient.ts`, `chunk-FV2JN4FK.mjs:306`). Fairtoll must pass a short `timeoutMs`, or a slow facilitator holds the page.
- Settlement happens after the origin responds, so the response is held until the facilitator confirms. A settle failure replaces the page with a 402.
- `createSettlementHeaders` sets only `PAYMENT-RESPONSE` (`chunk-FV2JN4FK.mjs:2822`). The stock middleware adds `Cache-Control: private` itself with `withPrivateCacheControl`. Fairtoll must do the same, or a shared cache can store a paid page and serve it to unpaid visitors. `charge.mjs` does, and `scenarios.mjs` asserts it.
- `isWebBrowser` decides between the HTML paywall and JSON by the `Accept` and `User-Agent` headers (`chunk-FV2JN4FK.mjs:3104`). For any browser request it also tries to `require("@x402/paywall")`, a large wallet UI bundle. Fairtoll should pass `customPaywallHtml` so that code never loads. `charge.mjs` does.

## How the server confirms payment without a key or custody

The server never signs anything, and no funds pass through it.

- `ExactEvmScheme` from `@x402/evm/exact/server` has no signer. Its constructor takes no arguments (`dist/esm/exact/server/index.mjs`). `charge.mjs` constructs it that way.
- The agent signs the transfer authorization. The facilitator holds the key that submits the transaction and pays gas. Its signer for `eip155:*` on `x402.org/facilitator` is `0xd407e409E34E0b9afb99EcCeb609bDbcD5e7f1bf`, as its `/supported` response lists.
- The authorization moves USDC from the payer to `payTo`, which is the publisher's wallet. The facilitator rejects any authorization whose `to` is not `payTo` (`invalid_exact_evm_recipient_mismatch`). It cannot redirect the funds, because the payer's signature covers the recipient and the amount.
- The server confirms payment from the facilitator's `/verify` result before it serves the page, and from the `/settle` result, which carries the transaction hash, before it releases the response. Fairtoll trusts the facilitator the publisher configured for this. It does not check the chain itself.

The publisher's config needs only a public wallet address for `payTo`. A mainnet facilitator does need an API credential (see below). That credential authenticates calls to the facilitator. It is not a wallet key and cannot move funds.

## Which facilitator a publisher configures

| Network | Facilitator | Config |
| --- | --- | --- |
| Base Sepolia testnet, `eip155:84532` | `https://x402.org/facilitator`, the `HTTPFacilitatorClient` default (`DEFAULT_FACILITATOR_URL`, `chunk-FV2JN4FK.mjs:305`) | None. |
| Base mainnet, `eip155:8453` | Coinbase CDP, `https://api.cdp.coinbase.com/platform/v2/x402` | A CDP API key ID and secret. `@coinbase/x402` (2.1.0) exports `createFacilitatorConfig(keyId, keySecret)`, which returns the `url` and `createAuthHeaders` that `HTTPFacilitatorClient` accepts. |

The public facilitator's `/supported` response, fetched on 2026-10-21, lists only testnets for EVM: `exact`, `upto`, and `batch-settlement` on `eip155:84532`. The CDP endpoint returns 401 without credentials.

Fairtoll's config should take a facilitator as `{ url, createAuthHeaders? }` and pass it to `HTTPFacilitatorClient` unchanged. That keeps Fairtoll out of facilitator choice, and the README rules out running one. `createAuthHeaders` must return headers keyed by path (`verify`, `settle`, `supported`). A flat headers object throws (`createAuthHeaders`, `chunk-FV2JN4FK.mjs:617`).

Do not add `@coinbase/x402` as a Fairtoll dependency. It pulls in `@coinbase/cdp-sdk`. A publisher who wants CDP can install it and pass its config.

## How testnet setup works

The testnet needs no account and no Fairtoll-side key:

1. Set the network to `eip155:84532` and the facilitator to the default `https://x402.org/facilitator`.
2. Set `payTo` to any wallet address the publisher controls. It receives Base Sepolia USDC.
3. To see a paid request succeed, a payer wallet needs Base Sepolia USDC. Circle's faucet at `https://faucet.circle.com` dispenses it. The payer's key belongs to the agent side, such as the setup CLI's test client, never to the server.

`run-testnet.mjs` runs `charge.mjs` against the live public facilitator with a freshly generated, unfunded payer key. The real `/supported` call succeeds, the 402 quotes Base Sepolia USDC, and the real `/verify` call rejects the payment for lack of funds:

```
402 accepts {"scheme":"exact","network":"eip155:84532","amount":"1000","asset":"0x036CbD53842c5426634e7929541eC2318f3dCF7e","payTo":"0x000000000000000000000000000000000000dEaD","maxTimeoutSeconds":300,"extra":{"name":"USDC","version":"2"}}
live facilitator verify rejected unfunded payer 0x7868...8db5 with: invalid_exact_evm_insufficient_balance
```

The spike did not settle a real testnet payment, because that needs a funded payer. The setup CLI task (#18) should run the same script with a faucet-funded payer to close that gap.

## Recommendations for the domain types and charging tasks

### Represent a price as an integer amount of the asset's smallest unit

`ExactEvmScheme.parsePrice` accepts three forms: a `"$0.002"` string, a JS number, or an `AssetAmount` of `{ amount, asset, extra }` in atomic units. The first two lose money without an error. `price-parsing.mjs` shows it:

```
"$0.002" -> 2000
"$0.0000004" -> 0
0.30000000000000004 -> 300000
"$1e-3" -> throws Invalid money format: $1e-3
```

`convertToTokenAmount` truncates digits past the asset's six decimals (`src/utils/index.ts`, `chunk-XW2CWVLZ.mjs:48-60`). A price below $0.000001 becomes a requirement for amount `0`.

The recommendation for #6:

- The config accepts a decimal USD string, such as `"0.002"`, because that is what a publisher writes.
- The config parser converts it to an integer count of micro-USD and rejects anything with more than six decimal places, a negative value, or zero. This is the only place a price is parsed.
- Inside Fairtoll a price is a branded type, such as `type Price = { readonly microUsd: bigint } & { readonly __brand: "Price" }`. The pricing hook returns this type, never a string or a number.
- The charge handler converts `Price` to an `AssetAmount` for the configured network's USDC: `{ amount: microUsd.toString(), asset, extra: { name, version } }`. The USDC address, name, and version per network come from one table in Fairtoll. Use the values in `@x402/evm`'s `DEFAULT_ASSETS` (`dist/esm/chunk-LQQ3M4DU.mjs`), for example `0x036CbD53842c5426634e7929541eC2318f3dCF7e` on Base Sepolia. The `/reports/` scenario passes an `AssetAmount` and the server quotes it unchanged.

USDC has six decimals on every network in `DEFAULT_ASSETS`, so micro-USD and atomic USDC are the same integer. If a later release adds an asset with different decimals, the conversion lives in that one function.

### Give the charge handler this shape

`charge.mjs` is a working sketch of it. For #11:

```ts
type ChargeOutcome =
  | { kind: "respond"; response: Response }
  | { kind: "paid"; serve: (origin: Response) => Promise<Response> };

function createCharger(config: { facilitator: FacilitatorConfig; network: Network; payTo: Address }): (request: Request, price: Price) => Promise<ChargeOutcome>;
```

- The handler takes a Fetch `Request` and a `Price` that the pricing hook already produced. It knows nothing about classes or policy.
- `respond` carries a 402, or a 412 for a Permit2 allowance, built from `x402HTTPResourceServer`'s instructions. The adapter returns that response as is.
- `paid` means the facilitator verified the payment. The adapter fetches the origin and passes the result to `serve`. `serve` cancels the payment on an origin status of 400 or higher and returns the origin response. Otherwise it settles and returns the response with `PAYMENT-RESPONSE` and `Cache-Control: private` set.
- The handler builds one `x402HTTPResourceServer` per config with the catch-all route, and it initializes lazily inside the first request.
- Facilitator errors and timeouts reject the promise. The pipeline from #10 catches them and fails open.

`charge.mjs` takes a `serve` callback instead of returning `paid`. Splitting it into two outcomes lets the pipeline own the origin fetch, which the Worker and Express adapters do differently.

### Decide what fail-open means for a paying agent

A facilitator outage while an agent pays leaves two choices. Fairtoll can serve the page unpaid, which is fail-open as the README states it, or it can return the 402 again. Serving it unpaid gives the content away during an outage. Returning the 402 contradicts "if the package throws, the page serves normally". The README's objective points to serving the page. Task #10 should state that choice in the pipeline and record the event, so the publisher sees unpaid serves in the event log.
